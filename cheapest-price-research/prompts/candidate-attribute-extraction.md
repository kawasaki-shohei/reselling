## タスク

中国輸入物販の最安値リサーチの第 5 段階 5-2 として、商品コード `{PRODUCT_CODE}` の 1 バッチ (50 件) の候補について、各候補の 7 軸属性を抽出する。

後段の機械照合 (5-3, `attribute-match-v2.js`) は、対象商品の属性 (`target_attributes.json`) と各候補の属性 (本タスクの出力) を軸ごとに比較し、**1 軸でも明らかに違えば候補から外す、unknown は通す** で絞り込む。比較は正規化付き (括弧書き除去・数値±10%許容・包含一致・色同義語) だが、**入力が綺麗なほど照合精度は上がる**。そのため:

- **判定不能な軸は無理に値を入れず null (color は `[]`)** を出すこと。null は後段で「unknown 扱い = 通す」になるので、誤った値を入れるよりも安全。ただし **null が多すぎる候補 (判明軸 2 以下) は「情報不足」枠に隔離され照合を通らなくなる** ので、画像から読み取れる軸は正直に埋めること
- **タイトルだけで決めず、必ず画像 (サムネ) も Read で見ること**。タイトル盛り盛り (例: 実物はフラットなサブバッグなのにタイトルに「キルティング」と書く) を画像優先で正しく判定する
- **短い一般語で書く**: 括弧書き `( )` の補足を付けない、多段修飾を重ねない (「回転式2段ピアス・ブレスレット収納スタンド」ではなく `回転式2段スタンド`)。size はタイトル/画像内表記の公称値のみ (実測しない)。material は 1 語のみ。補足したい観察は `reason` に書く
- **サムネ画像内に採寸・寸法バナー (「直径16cm」「高さ28.2cm」等) が写っていたら、必ず size に拾うこと**。過去 run で、画像に採寸が明記されていたのに size を null にしたため、サイズ違いの類似品 (直径 20.5cm vs 16cm) を機械照合で弾けず画像最終確認まで流してしまった実例がある (2026_07_21_21_50 / FE05201)

## 7 軸属性の定義

| 軸 | 説明 | 例 | 不明時 |
|---|---|---|---|
| `category` | 粗ジャンル | トートバッグ / サングラス / ロングリード | null |
| `subcategory` | 用途・機能修飾を含む細名 | マザーズバッグ / ウェリントン型 / 訓練用 | null |
| `color` | 色 (配列) | `["黒"]` / `["ブラック", "白"]` | `[]` |
| `size` | サイズ | `"A4"` / `"10m"` / `"80×120"` | null |
| `quantity` | 個数・セット数・容量 | `"1個"` / `"2個セット"` / `"100枚"` | null |
| `pattern` | 柄 | `"無地"` / `"花柄"` / `"ひし形キルティング"` | null |
| `material` | 素材 | `"ナイロン"` / `"合皮"` / `"プラスチック"` | null |

各軸の粒度ルールと粒度感は `target-attribute-extraction.md` の「7 軸属性の定義」セクションと同じ。両者は機械照合で比較されるので、**実質同じ意味なら対象側で使われている表記に揃える** こと (正規化があるとはいえ、表記が揃っているに越したことはない)。

なお `material` は機械照合の棄却軸から外れている (参考情報扱い)。サムネで素材を断定するのは困難なため、確信が無ければ null で構わない。

## 画像優先の原則 (必読)

タイトルと画像で矛盾がある場合は **画像を優先** する。出品者がタイトルを盛る/誤記することがあるが、画像は実物そのものを示す。

具体例 (実際にあったケース):
- タイトル「キルティング トートバッグ ブラック A4対応 軽量 大容量 通勤」だが画像は完全にフラットなサブバッグ (画像内に「フォーマルサブバッグ BLACK」と書いてある) → `pattern: "無地"`, `subcategory: "フォーマルサブバッグ"` (画像優先)

## 対象商品の属性 (基準データ、参考)

呼び出し側が `target_attributes.json` の該当商品分 (`{PRODUCT_CODE}` の attributes) を inline で渡す。これは **抽出の基準ヒント** として使ってよい (例: 対象が `color: ["黒"]` なら、候補の色も「黒系」を意識して抽出)。

ただし、**「対象に合わせて候補の属性を歪める」のは禁止**。各候補は独立に、その候補自身の実物属性を抽出する。機械照合 (5-3) で「同じ表記なら一致、違えば不一致」と判定するため、対象に揃えるよう恣意的に書くと正しい判定ができなくなる。

例:
- 対象 `color: ["黒"]`、候補画像が白 → 候補 `color: ["白"]` を出す (対象に合わせて「黒」と書かない)
- 対象 `pattern: "ひし形キルティング"`、候補画像が部分キルティング → 候補 `pattern: "部分キルティング"` を出す (対象と異なる属性を正直に書く)

## 入力

### 候補一覧

- `{RIVALS_JSON_ABS_PATH}` (= `rivals/page_{PAGE_NO:02d}.json`) を Read
- 構造: `{ page, items: [{ rank, id, name, price, thumbnails, ... }, ...] }`
- `items[]` の各要素について、rank と name と price を抽出基準のテキスト情報として使う

### 候補画像 (サムネ)

各候補について `{THUMBS_DIR_ABS_PATH}/{rank:02d}.jpg` を Read で画像認識する (1 候補 = 1 サムネ画像)。

### 対象属性 (基準ヒント)

呼び出し側が `{PRODUCT_CODE}` の attributes (7 軸) を inline で渡す。

## 出力

`{OUTPUT_JSON_ABS_PATH}` (= `candidate_attributes/page_{PAGE_NO:02d}.json`) に以下の構造で書き出す:

```json
{
  "page": 1,
  "extractedAt": "2026-05-28T10:30:00+09:00",
  "productCode": "FD01101",
  "candidates": [
    {
      "rank": 1,
      "id": "m16332362187",
      "name": "キルティング トートバッグ ブラック A4対応 軽量 大容量 通勤 黒 通学",
      "price": 610,
      "attributes": {
        "category": "トートバッグ",
        "subcategory": "フォーマルサブバッグ",
        "color": ["黒"],
        "size": "A4",
        "quantity": "1個",
        "pattern": "無地",
        "material": "ポリエステル"
      },
      "reason": "画像でフラットな無地のサブバッグを確認。タイトルに「キルティング」とあるが画像優先で「無地」と判定。"
    },
    {
      "rank": 6,
      "id": "m37040454091",
      "name": "...",
      "price": 1080,
      "attributes": { ... },
      "reason": "..."
    }
  ]
}
```

- `candidates[]` には **バッチ内の全 50 件** を網羅すること (途中で省略しない)
- `attributes` の 7 軸を全て埋める (判定不能なら null または `[]`)
- `reason` は判定根拠を 1〜2 文。画像優先で判定したケースは必ず明記

## バッチ逐次保存 (中断耐性の要)

候補ごとに以下を繰り返し、**1 候補の判定が終わるごとに即 OUTPUT_JSON を書き直し** すること。まとめて一括書き出しは禁止 (中断で判定がロストする、親 Cowork は書き出されたファイルしか見ない)。

実装方法:
1. 出力 JSON `{OUTPUT_JSON_ABS_PATH}` に空の `{page, extractedAt, productCode, candidates: []}` を書き出す
2. rivals/page_NN.json の `items[]` を順に処理:
   - rank に対応する `{THUMBS_DIR_ABS_PATH}/{rank:02d}.jpg` を Read で画像認識
   - 7 軸属性を判定
   - 出力 JSON を Read してから現候補の entry を candidates[] に追加して Write (全件再書き出し)
3. 全候補完了したら完了報告

## 完了報告

出力 JSON を書き終えたら、以下を報告する:

- 出力 JSON のパスと候補数 (`candidates[]` の長さ)
- rivals/page_NN.json の items 数 (期待値、通常 50 件)
- 件数が一致しているか
- 各属性軸ごとに null 件数 (どの軸が判定不能になりやすいか)
- 「画像優先で判定を反転した」ケース (例: タイトル「キルティング」だが画像で「無地」) があれば全件報告
- スポットチェック用に「対象との一致が期待できそうな候補」を 2〜3 件抜粋

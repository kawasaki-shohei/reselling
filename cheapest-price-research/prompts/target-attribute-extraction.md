## タスク

中国輸入物販で、メルカリで現在販売中の同一商品の最安値を調査するリサーチを行う。その第 3 段階として、各対象商品の **7 軸属性** を抽出する。

後段の第 5 段階 (機械照合) では、本タスクの出力 `target_attributes.json` を **「正」の基準** として、各候補の 7 軸属性と機械的に比較する。1 軸でも明らかに違えば対象外、unknown は通す、というルールで絞り込みを行う。

そのため本タスクでは、**判定不能な軸は無理に値を入れず null (color は `[]`)** を出すこと。null は後段で「unknown 扱い = 通す」になるので、誤った値を入れるよりも安全。

## 【最重要】attributes は照合キー、詳細は attributes_detail に分けて書く

`attributes` の 7 軸は **機械照合の比較キー** である。候補側の出品者は商品説明の公称値・一般的な語しか書かないため、こちらが具体的に書くほど一致しなくなる。過去 run (2026_07_21_21_50) では `約14.5cm` (画像実測) vs `15cm` (公称)、`PUレザー(合皮)` vs `PUレザー` のような差で **同一商品が機械照合で全滅し、対象商品自身の出品まで棄却される事故** が起きた (run_notes §8.3)。

`attributes` の記述規律:

1. **括弧書き `( )` を付けない** (補足したいことは attributes_detail へ)
2. **画像からの実測値を書かない** (タイトル/説明文の公称値のみ。公称が無ければ null)
3. **短い一般語で書く** (`無地` / `2XL` / `30枚` / `キルティング` のように。「〜(スナップ開閉)」のような仕様補足を混ぜない)
4. 迷ったら null (unknown は照合を通るので、具体的すぎる値より安全)

その代わり、**画像から読み取った詳細情報は `attributes_detail` (自由記述) に必ず書く**。この欄は機械照合には使われず、第 6 段階 (画像最終確認) の判定材料としてそのまま Sonnet に渡される。過去 run では「直径約20.5cm」の実測値が同型の直径16cm品を見破る決め手になり、「COPY 刻印なし」の観察が刻印違いの検出に効いた。**詳細を捨てるのではなく、書く場所を分ける**こと。

attributes_detail に書くべきもの: 画像実測の寸法、刻印・ロゴ・タグの内容、留め具/開閉方式、内部構造 (仕切り・フック数等)、付属品構成、背面/裏面の形状、複合素材の内訳、その他その商品を同型類似品から見分けるポイント。

## 同一商品判定の前提 (必読)

メルカリの中国輸入品は、出品者が他出品者通報リスクを避けるためタイトル・画像・説明文を意図的に変えて出品する慣習がある。よって「タイトル文字列の一致」ではなく **実体属性 (色・サイズ・個数・セット数・柄・素材・用途) の一致** で同一商品を判定する。

## 7 軸属性の定義

| 軸 | 説明 | 取得元 | 例 | 不明時 |
|---|---|---|---|---|
| `category` | 粗ジャンル | タイトル / 説明文 / 画像 | トートバッグ / サングラス / ロングリード / 平干しネット | null |
| `subcategory` | 用途・機能修飾を含む細名 (category と同じなら category と同値) | タイトル / 説明文 / 画像 | マザーズバッグ / ウェリントン型 / 訓練用 / ハーフムーン型 | null |
| `color` | 色 (配列、複数色なら全部) | **画像で判定**、タイトル / 説明文で補完 | `["黒"]` / `["ブラック", "白"]` / `["ベージュ"]` | `[]` |
| `size` | サイズ (寸法・規格) | タイトル / 説明文 (画像内に書かれていれば画像も) | `"A4"` / `"10m"` / `"80×120"` / `"25cm"` / `"XL"` | null |
| `quantity` | 個数・セット数・容量 | タイトル / 説明文 | `"1個"` / `"2個セット"` / `"5枚セット"` / `"100枚"` / `"500g"` | null |
| `pattern` | 柄 | **画像で判定**、タイトル / 説明文で補完 | `"無地"` / `"花柄"` / `"チェック"` / `"迷彩"` / `"ひし形キルティング"` | null |
| `material` | 素材 | 説明文、画像での質感 | `"ナイロン"` / `"合皮"` / `"本革"` / `"プラスチック"` / `"ポリエステル"` | null |

### 軸ごとの粒度ルール

- `category`: ジャンルとしての分類。「トートバッグ」「サングラス」「ロングリード」「ピアス」「Tシャツ」など、機能・用途修飾を含まないジャンル名
- `subcategory`: 機能・用途・型修飾を含む細分類。「マザーズバッグ」「ウェリントン型サングラス」「犬用訓練リード」など。**修飾は 1 つまで** (「回転式2段ピアス・ブレスレット収納スタンド」のような多段修飾は不可 → `回転式2段スタンド` 程度に留め、残りは attributes_detail へ)。category と同じなら null でも category 同値でも可 (機械照合では同じ扱いになる)
- `color`: 必ず配列。実物画像で見える色全てを入れる。アクセント色も含める (例: 黒地に白文字 → `["黒", "白"]`)
- `size`: **タイトル/説明文の公称値のみ**を「数字 + 単位」または「規格名」で入れる (例: `"10m"`, `"A4"`, `"L"`, `"2XL"`, `"15cm"`)。**画像からの実測値は入れない** (attributes_detail へ)。公称値が無ければ null
- `quantity`: 個数の単位 (個 / 枚 / 本 / 点 など) も含める (例: `"5枚セット"`, `"1本"`)。セット内容の内訳 (「ラケット2本+ケース1個+玉3個」等) は主たる数だけ書き、内訳は attributes_detail へ
- `pattern`: 主たる柄を **短い 1 語** で (「無地」「花柄」「キルティング」)。「無地」も柄の一種として明示 (null ではなく `"無地"`)。質感補足 (「(型押しレザー調)」等) は付けない
- `material`: 主素材を 1 つ。複合素材なら主たるもの **1 語のみ** (例: 表地が合皮なら `"合皮"`。`"ポリカーボネート+スチール"` のような複合表記は不可、内訳は attributes_detail へ)

## 画像優先の原則 (必読)

タイトル / 説明文 と画像で矛盾がある場合は **画像を優先** する。タイトル・説明文は出品者が誤記・省略することがあるが、画像は実物そのものを示す。

具体例:
- タイトル「キルティング トートバッグ ブラック A4対応」だが画像は完全にフラットなサブバッグ → `pattern: "無地"` (画像優先)
- タイトル「宅配ビニール袋 B4 100枚 白」だが画像は黒、description にも「カラー: ブラック」明記 → `color: ["黒"]` (画像優先)
- タイトル「サングラス」だが画像でウェリントン型と確認 → `subcategory: "ウェリントン型サングラス"` (画像で詳細補完)

## 入力

### 対象商品コード一覧

呼び出し側が処理対象の商品コード一覧を inline で指定する (20 件)。本プロンプトでは source.csv を Read しない (呼び出し側が必要な情報を inline で渡す前提)。

### 各商品の入力ファイル

- **対象詳細 JSON**: `{TARGET_DETAIL_DIR_ABS_PATH}/{商品番号}.json` を Read
  - 構造: `{ id, name, price, description, photos (URL 配列), seller, item_condition, ... }`
  - 特に `name` (タイトル)、`description` (商品説明文全文)、`item_condition` を参照
- **対象画像**: `{TARGET_IMAGES_DIR_ABS_PATH}/{商品番号}/photo_N.jpg` を Read で画像認識
  - photo_1.jpg から photo_M.jpg まで (M は photos[].length)
  - **全画像を Read すること** (1 枚目だけでは詳細が判らない場合がある)

## 出力

`{OUTPUT_JSON_ABS_PATH}` (= `target_attributes.json`) に以下の構造で書き出す:

```json
{
  "extractedAt": "2026-05-28T10:00:00+09:00",
  "products": {
    "FD00301": {
      "id": "m85899014828",
      "name": "犬 ロングリード 10m 訓練用 トレーニング 大型犬 中型犬 黒",
      "attributes": {
        "category": "ロングリード",
        "subcategory": "犬用訓練リード",
        "color": ["黒"],
        "size": "10m",
        "quantity": "1本",
        "pattern": "無地",
        "material": "ナイロン"
      },
      "attributes_detail": "幅約2.5cm(画像実測)。金具はシルバーの回転ナスカン、持ち手側にループあり。タグ等の刻印なし。",
      "reason": "画像で黒・ナイロン製の長尺リードを確認。タイトル・説明文と一致。"
    },
    "FD01101": {
      "id": "m39658698781",
      "name": "...",
      "attributes": { ... },
      "reason": "..."
    }
  }
}
```

- ルート: `extractedAt` (ISO 8601 文字列、JST) + `products` (商品番号をキーとしたオブジェクト)
- 各商品: `id` (Mercari item id), `name` (target_detail の name そのまま), `attributes` (7 軸オブジェクト、照合キー規律に従う), `attributes_detail` (自由記述、第 6 段階用の識別ポイント), `reason` (判定根拠 1〜3 文)
- `reason` には「画像で何を確認したか」「タイトル/説明文との一致/矛盾」を簡潔に書く

## バッチ逐次保存 (中断耐性の要)

商品ごとに以下を繰り返し、**1 商品の判定が終わるごとに即 OUTPUT_JSON を書き直し** すること。まとめて一括書き出しは禁止 (中断で判定がロストする、親 Cowork は書き出されたファイルしか見ない)。

実装方法:
1. 出力 JSON `{OUTPUT_JSON_ABS_PATH}` に空の `{extractedAt, products: {}}` を書き出す
2. 呼び出し側から渡された商品コード一覧を順に処理:
   - `{TARGET_DETAIL_DIR_ABS_PATH}/{商品番号}.json` を Read
   - `{TARGET_IMAGES_DIR_ABS_PATH}/{商品番号}/photo_N.jpg` を全枚数 Read
   - 7 軸属性を判定
   - 出力 JSON を Read してから現商品の entry を追加して Write (全件再書き出し)
3. 全商品完了したら完了報告

## 完了報告

出力 JSON を書き終えたら、以下を報告する:

- 出力 JSON のパスと商品数 (`products` のキー数)
- 入力 source.csv の商品数 (呼び出し側から渡された一覧の件数)
- 件数が一致しているか
- target_detail / target_images の Read エラーが発生した商品があれば一覧
- スポットチェック用に 5〜10 件抜粋して「商品名 → 7 軸属性」のマッピングを示す
- 各属性軸ごとに null 件数を報告 (どの軸が判定不能になりやすいかの把握)
- 「画像優先で判定を反転した」ケース (例: タイトルと色が食い違い、画像優先で反転) があれば全件報告

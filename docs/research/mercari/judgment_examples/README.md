# judgment_examples/ の主旨

## このディレクトリの目的

メルカリ売れ筋リサーチのクラスタリング (似た商品を 1 つの売れ筋としてまとめる / 別々にする) で、**実際に判定に迷ったケースを実物の商品ページと共に記録する場所**。

後で同じような商品に遭遇したときに、過去の判定結果を参照して一貫性を保つため。

## 前提知識: タイトル・画像・説明文は同一商品判定の最終根拠ではない

中国輸入品は同じ商品を複数の出品者が扱うが、出品者は **他出品者のコピーとして通報されるリスクを避けるため**、タイトル・画像・説明文を故意に変えて出品する慣習がある (画像を撮り直す、説明文を書き直す、タイトルの語順や語句を入れ替える 等)。

よって、タイトルが異なっていても、または画像が違って見えても、**実体 (色・サイズ・個数・セット・素材・用途・柄) が一致すれば同一商品** として扱う。逆に、タイトルや画像が似ていても実体が違えば別商品。各判定例ではこの原則に基づいて「属性テーブル」「比較表」で実体を見る構造にしている。

**この一覧 (色・サイズ・個数・セット・素材・用途・柄) が判定軸の一般則である**。これが判定ルールの正典であり、このディレクトリの中で最も重要な一行。

## このディレクトリを読むときの注意 (重要)

よくある誤読を先に潰しておく。新セッションの Claude が過去に実際に引っかかった内容。

### 誤読パターン: 「ファイル一覧 = 判定軸の全集」と思ってしまう

判定例ファイル (`色違いは別商品.md`、`個数違いは別商品.md` 等) のラインナップを見て、「ここに `.md` ファイルがある軸が判定軸の全てだ」と推論するのは **誤り**。

このディレクトリは 2 つの役割を兼ねている:

1. **一般則の宣言** — 前節「前提知識」の 1 行 (実体属性列挙)
2. **困難例の記録** — 各 `*.md` ファイル (迷ったときの実物記録)

**ファイル一覧は 2 の結果にすぎず、1 を網羅していない**。ファイルが存在しない判定軸も一般則としては当然に存在する。

### 具体例: 「素材違いは別商品.md」が無いのはなぜか

`素材違いは別商品.md` というファイルは存在しない。しかしこれは「素材は判定軸ではない」という意味では **決してない**。後述の運用ルール「判定に迷わない自明な例は記録しない」に従った結果、本革 vs 合皮・綿 vs ポリエステルのような誰が見ても別物と分かる素材違いが記録されていないだけ。素材違いは一般則として当然に別商品扱いである (前節 L13 の列挙に「素材」が含まれている)。

### 判定軸を確認したい時の正しい参照先

- **一般則の根拠** → 前節「前提知識」L13 の実体属性列挙 (色・サイズ・個数・セット・素材・用途・柄)。これが正典
- **困難例の具体** → 各 `*.md` ファイル。**ただし網羅ではない。ファイルが無い軸でも一般則は適用される**

「ここに `.md` ファイルが無いから判定軸ではない」「このディレクトリに書かれていないケースは判定対象外」と判断するのは誤りなので注意。

## 入れるもの

- **同一商品か別商品かの判定で迷ったケース** (実際にリサーチやフィードバックで遭遇したもの)
- 商品 A / B のスクリーンショット + タイトル + 価格 + 出品者 ID
- 比較表 (属性ごとに一致 / 違いを可視化)
- 判定結果 (同一商品として扱う / 同一商品として扱わない)
- 判定の簡潔な理由

## 入れないもの (他ファイルに振り分け)

| 種類 | 入れる先 |
|---|---|
| ブランド品・キャラクター・食品・薬機法対象など、タイトルで機械的に除外できる商品 | `../../../../procedures/exclude_by_keywords/keywords.json` (実行用辞書) + `references/注意商品.pdf` / `references/new仕入れ禁止商品_アパレル.pdf` (設計原則は `../keywords_design_notes.md`) |
| ライバル数カウントのルール (更新日時 2 週間以上前は非カウント 等) | 別ドキュメント (`procedures/mercari-research.md` 等、未作成なら作る) |
| 自動クラスタリングの実装方針・アルゴリズム | `../implementation-notes.md` 等 |
| 推測で「こういうケースも想定できる」という机上の検討 | このディレクトリには入れない (実遭遇ベースのみ) |

## 運用ルール

- **実際にリサーチやフィードバックで遭遇したケースだけを記録する**。推測で「こういうケースもあるかも」は入れない
- **商品を選ぶときは必ず画像を確認する**。タイトルが似ているだけで同一商品扱いにすると、実体は全く別商品というケースがある (例: タイトルに「レインコート レインポンチョ」が併記されていても、形状・袖・フードの有無で別商品)
- **判定に迷わない自明な例は記録しない**。例えば「厚手不透明の袋」と「薄い透明 OPP 袋」のように画像を見れば瞬時に別物と分かる商品を並べても、判定例として学習価値がない
- 新しい判定ケースに遭遇したら、判定内容を表す日本語ファイル名で新ファイルを作る
- 既にあるカテゴリでも、角度が違えば別ファイルを作ってよい
- ケースが明らかに不要・誤りと判明したら削除してよい (経緯は git 履歴で残る)

## ファイル命名規則

```
{内容を短く表す日本語}.md
```

例:
- `色違いは別商品.md`
- `個数違いは別商品.md`
- `セット枚数違いは別商品.md`

## フォーマット (既存ファイル準拠)

各判定例ファイルの構成:

1. **冒頭**: 判定結果 (同一商品として扱う / 扱わない)
2. **商品 A**: スクリーンショット + 属性テーブル (タイトル・URL・価格・出品者・サイズ・色・用途 等)
3. **商品 B**: 同上
4. **比較表**: 属性ごとに A / B を並べて、一致 (○) / 違う (✗) を可視化
5. **判定**: 結論と簡潔な理由
6. **この例の注釈** (必要なら): 例の限界や周辺の別ルールへの言及

## スクリーンショットの保存先

```
judgment_examples/images/{判定例名}_{a|b|c}_{商品特徴}_seller{出品者ID}.png
```

viewport スクリーンショット (スクロール無し) を基本とする。商品説明文まで写したい場合は fullPage を使う。

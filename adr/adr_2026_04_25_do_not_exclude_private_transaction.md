# ADR: private_transaction カテゴリの復活

## ステータス

採用 (Accepted) — 2026-04-19

## コンテキスト

### 前段 (2026-04-18 の廃止決定)

旧辞書には `private_transaction` カテゴリが存在し、「〇〇様専用」「様リクエスト」「♪*★様」等の取引専用ページ表記を除外していた。2026-04-18 のセッションで、仕入れ判断者から「取引専用ページは別に除外しなくていい」という明示指示があり、`private_transaction` カテゴリは完全廃止された (分類カテゴリが 9 種類 → 8 種類になった)。

この廃止判断は「取引専用ページでも第三者が購入できる場合があり、仕入れ候補から機械的に外す理由はない」という観点に基づいていた。

### 再検討のきっかけ (2026-04-19)

2026-04-19 のセッションで `keywords.json` の改善を進める中、4/16 のリサーチデータで「様」を含む unflagged タイトルが **582 件** (unflagged 総数 5,197 の 11.2%) 存在することを発見。内容を詳細に確認すると:

- メルカリの**商品タイトルは 40 字制限**という仕様がある (メルカリ公式ヘルプ・各種解説記事で確認)
- タイトル先頭が「〇〇様 専用」「〇〇様 リクエスト」で占められると、商品情報 (色・サイズ・セット数・素材等) を書くスペースが削られる
- 4/16 データで「様」を含む unflagged のうち、**タイトル 16 字以下 (情報希薄) = 112 件**
- 例: `★様専用` (4 字)、`♡様専用ページ` (7 字)、`【Sakura様専用】黒5点` (14 字) 等

つまり、**取引専用ページ表記があるタイトルは仕入れ判断に必要な情報が欠落しており、タイトルだけでは商品を特定できない**ケースが多い。これは 2026-04-18 の廃止決定時には検討されていなかった観点。

### 4/16 データでの調査結果

- 「様 + 専用」(両方含む) = 195 件。`お客様専用` 2 件が誤爆候補だったが実態は取引専用で誤爆なし
- 「様 + リクエスト」(両方含む) = 192 件。誤爆候補ゼロ
- 「様」単独 (専用/リクエスト含まず) = 298 件 (挨拶・敬称の「様」、除外対象外)

## 代替案

### 案 A: 既存カテゴリに混入 (brand_imitation 等)

- メリット: カテゴリ数 8 のまま維持、手順書更新最小
- デメリット: 意味論が崩れる (`brand_imitation` は「ブランド模造品」のカテゴリ)
- **却下理由**: 設計的に不純。将来のメンテナンスで混乱する

### 案 B: 情報希薄判定 (タイトル文字数ベース)

- 「タイトル 16 字以下」など文字数ベースで機械的除外
- メリット: 様専用以外の情報希薄パターンもカバー可能
- デメリット: 辞書ベース `.includes()` の実装では不可能、スクリプト側の改修が必要
- **却下理由**: 複雑さ増加。まず取引専用の網羅で十分な効果あり。必要なら後で拡張

### 案 C: 現状維持 (2026-04-18 方針)

- メリット: 変更ゼロ
- デメリット: 仕入れ候補プールに判断不能な行が 582 件 (11.2%) 残り続け、後段 (主要ワード抽出 / クラスタリング / ライバル調査) のトークン・画像 Read コストが無駄になる
- **却下理由**: 情報欠損問題が明確で、仕入れ判断者にとっても判断不能な行を 500 件以上見せることは負担

### 案 D (採用): 新カテゴリ復活 + withAll 組み合わせ判定

`private_transaction` カテゴリを復活、priority 末尾に配置。withAll で「様 + 専用」「様 + リクエスト」の組み合わせで除外。

## 決定事項

### 実装

[`../procedures/exclude_by_keywords/keywords.json`](../procedures/exclude_by_keywords/keywords.json) の:

1. `priority` 配列の末尾に `"private_transaction"` を追加
2. `keywords` 内に新カテゴリを追加:

```json
"private_transaction": [
  { "keyword": "様", "withAll": ["専用"] },
  { "keyword": "様", "withAll": ["リクエスト"] },
  { "keyword": "さま", "withAll": ["専用"] },
  { "keyword": "さま", "withAll": ["リクエスト"] }
]
```

### 選んだ理由

- **withAll 組み合わせ判定** により、順序・間のスペース・間のワードを問わず「様 ○○ 専用」のような表記もカバー
- **priority 末尾**: 法令違反ではないため、法令リスクカテゴリの後ろに配置
- **「様専用」「様リクエスト」のみ対応**: 誤爆を避けるため、組み合わせ前提で「様」単独マッチは起こさない

## 結果

### 期待される効果 (メリット)

- 4/16 データで **364 件** が仕入れ候補から外れ、仕入れ判断者の負担減
- 後段 (主要ワード抽出 / クラスタリング) で処理する件数が減り、トークン消費も減る
- 情報欠損問題の網羅的な解決

### トレードオフ (デメリット)

- **情報あり長いタイトルも除外される**
  - 例: 「Rose様専用】車内カーテン 2点 ブラック 2枚セット 日除け 目隠し 遮光」(40 字フル)
  - ただし、本質的に取引専用ページは他人向けの個別出品で、第三者購入で運用トラブルのリスク
  - タイトルに情報があっても仕入れ対象にする意義は薄い
- **仕入れ判断者の 2026-04-18 指示を部分的に覆す**
  - 当初の観点「取引専用は別にダメじゃない」に対し、「情報欠損で判断不能」という新観点で判断を更新
  - 仕入れ判断者の明確な再確認は取っていない (判断依頼 md を別途作成してもよい)

### 将来的な考慮事項

- **「様専用」「様リクエスト」以外の取引専用表記**:
  - 「〇〇さん専用」「ヒロ様」「♪*★様 + アイスヤーン」のように「専用」「リクエスト」以外の表記
  - 現在は withAll 非対応のため漏れる (精度再測定で FN 発生を確認)
  - 必要性が出たら別エントリを追加
- **「お客様専用 + 商品」のような誤爆**:
  - 現在 4/16 データで該当 2 件、いずれも実質取引専用で誤爆なし
  - 将来誤爆が発生したら notWith で対処
- **仕入れ判断者への再確認の必要性**:
  - 本 ADR は「情報欠損」観点で判断を更新したが、仕入れ判断者の明示合意は未取得
  - 仕入れ判断者が前回の「除外しなくていい」指示を維持する意向であれば、本決定は撤回の可能性あり

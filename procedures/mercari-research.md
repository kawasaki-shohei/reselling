## 採用中の検索手法: 14日ウィンドウ方式

Mercari内部APIを直接呼び出し、14日以内にSOLDになった全商品を収集・クラスタリングすることで売れ筋を特定する方式。

**実績（2026-04-12）**: 全10キーワード × 5価格帯 = 50組み合わせを約3分で完走。7,152件収集・23品の仕入れ候補を特定。トークン消費は軽微。

---

### ロジック概要

1. 入口キーワード（10種）× 価格帯（5区間）の組み合わせを並列で実行する
2. 各組み合わせについて、`SORT_CREATED_TIME DESC` + `STATUS_SOLD_OUT` + `itemConditionId=[1]` でSOLD一覧をAPI取得する
3. **14日境界**（現在時刻 - 14×86400 秒）に達するまで全ページを収集する
4. 全組み合わせの収集結果を `item.id` でユニーク化する
5. タイトルを正規化してクラスタリングし、3件以上のクラスターを売れ筋候補とする
6. 除外PDFと突合して禁止商品を除外する

---

### 価格帯の区切り

5区間 × 10キーワード = **50組み合わせ**を実行する。区間を小さくするほど1バケット内の件数が減り、14日境界に到達しやすくなる。

| 区間 | 範囲 |
|---|---|
| 1 | ¥800〜¥1,000 |
| 2 | ¥1,000〜¥1,200 |
| 3 | ¥1,200〜¥2,000 |
| 4 | ¥2,000〜¥3,000 |
| 5 | ¥3,000〜¥5,000 |

---

### 手順の全体フロー

**収集・分析のコードを自分で書かないこと。必ず以下のスクリプトを使うこと。**

```
research/collect.js   ← 収集（browser_evaluate で実行）
research/analyze.js   ← 分析（node で実行）
```

1. `browser_navigate` で `https://jp.mercari.com` の任意のページを開いて3秒待つ
    - 未ログインでよい。`collect.js` が DPoP 認証キーを IndexedDB から取得するため、ブラウザで Mercari のセッションを確立しておく必要がある
2. `research/collect.js` の内容を読み取り、`browser_evaluate` の `function` パラメータにそのまま渡して実行する
3. 戻り値の `_filename` フィールドの値を使い、`research/` ディレクトリに JSON として保存する
4. `node research/analyze.js research/<保存したファイル名>` を実行する
5. 第3段階（禁止商品チェック・手動・PDF突合）を実施する（下記「第3段階: 禁止商品チェック（手動・PDF突合）」参照）
6. レポートを作成する（下記「レポート化（手動）」参照）

---

### 収集後処理

`analyze.js` が2段階の自動パイプライン（**第1段階**: タイトル正規化によるクラスタリング、**第2段階**: 価格一貫性・カテゴリ多数決・出品者数のメタデータフィルタ）で候補を絞り込み、その後、手動の禁止商品チェック（第3段階）とレポート化を行う。第1・第2段階の内部実装は [`docs/research/implementation-notes.md`](../docs/research/implementation-notes.md) を参照。

**`analyze.js` の出力**: 入力と同じディレクトリ（`research/`）に以下の2ファイルを生成する。

- `YYYY_MM_DD_HH_MM__candidates.json` — 3件以上のクラスターをメタデータ付きで格納（レポート化に使う主ファイル）
- `YYYY_MM_DD_HH_MM__clusters.json` — 全クラスターの概要（デバッグ用）

**`candidates.json` の `candidates` 配列の主要フィールド**:

| フィールド | 意味 |
|---|---|
| `representativeTitle` | 代表タイトル（1件目のアイテム名） |
| `count` | クラスター内のアイテム数（カテゴリフィルタ後） |
| `minPrice` / `maxPrice` | 価格帯 |
| `priceWarning` | 価格幅が2倍超（別商品混入の可能性あり・要目視確認） |
| `uniqueSellers` | ユニーク出品者数 |
| `excluded` | 除外フラグ（`true` の場合はレポート本文から除外し、末尾の除外一覧に記載する） |
| `exclusionReason` | 除外理由（例: `"sellers_10_or_more"`） |
| `thumbnails` | 代表サムネイルURL（最大3枚） |
| `items` | クラスター内の全アイテム（`id`・`name`・`price`・`url`・`sellerId`・`categoryId`・`thumbnail`） |

#### 第3段階: 禁止商品チェック（手動・PDF突合）

仕入れ候補から、法務・コンプライアンス上の禁止商品を除外する。**このチェックを通過しない候補はレポートに載せてはいけない**（ゲート条件）。

**手順:**

1. `references/注意商品.pdf` と `references/new仕入れ禁止商品_アパレル.pdf` を**全ページ、画像を含めて**読む
   - セッションメモリは持続しないため、毎回読み直す
   - テキスト抽出では拾えない情報（ロゴ・キャラクターデザイン・類似例）があるため画像も目視する
2. `*_candidates.json` の各候補について、タイトル・サムネイルをPDFの内容と突合する
3. 以下のカテゴリに該当するものは除外する:
    - ブランドロゴ／キャラクター／版権物／模倣品
    - PSE該当品（電気用品）／薬機法該当品（化粧品・医薬品等）／食品衛生法該当品
    - 動物素材（毛皮・ワシントン条約該当品等）
4. 除外した候補は**レポート末尾に「禁止商品チェックで除外」として件数・代表タイトル・除外理由を記録する**（トレーサビリティのため）

### レポート化（手動）

第3段階を通過した候補をレポート化する。**この段階ではClaudeがクラスターの統合・分割・同一性判定を行わない**（ADR `adr/adr_2026_04_12_Claudeによるクラスター検証ステップの導入.md` で却下済み。理由: 第1段階の精度が95%+で不要な一方、介入による候補消失リスクのほうが大きい）。

**手順:**

1. `*_candidates.json` の `candidates` 配列を順番に処理する（上限なし・全件）
2. `excluded: true` フラグ付きクラスター（`exclusionReason: "sellers_10_or_more"`）は仕入れ候補から除外し、レポート末尾に「競合過多で除外したクラスター」として件数・代表タイトルを記録する
3. 第3段階（禁止商品チェック）で除外された候補もレポート末尾に件数・代表タイトル・除外理由を記録する
4. 残った候補を `reports/YYYY/MM/` に Markdown で保存する

**絶対禁止事項:**

- `slice(0, N)` や「上位のみ」「厳選」「代表的なもの」等の理由で候補を間引くこと。**`excluded: true` と第3段階で除外した以外の候補は全件レポートに掲載する**
- タイトル・サムネイルを見て「これは同一商品ではない」「これは別商品」等の意味判断でクラスターを分割・統合・除外すること。クラスタリングの誤りはすでに第1段階の recall 重視方針で許容している（価格幅⚠️フラグで識別可能）

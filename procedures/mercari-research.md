### やりたいこと

① メルカリで中国輸入製品商品を調査する

条件：
- ブランド模造他、除外条件に合致しないもの（→ 第3段階で判定）
- 2週間に3個以上の販売実績があるもの（→ 第1段階の `analyze.js` で判定）
- 同商品の販売者数10人未満のもの（→ 第4段階の `rival_count.js` で判定）


### 同一商品判定の前提

メルカリの売れ筋リサーチでは、**「タイトル・画像・説明文が一致する商品だけが同一商品」ではない**。中国輸入品は同じ商品を複数の出品者が扱うが、出品者は以下の理由でタイトル・画像・説明文を故意に変えて出品する:

- **他出品者のコピーとして通報されるリスクを避けるため**
- 画像を自分で撮り直したり、説明文を自分なりに書き直したり、タイトルの語順を入れ替えたりする
- つまり **タイトル・画像・説明文が別でも、実体 (色・サイズ・個数・セット・素材・用途・柄) が一致すれば同一商品**

よって同一商品判定は最終的にタイトル文字列ではなく **実体属性の一致** で行う必要がある。具体的な属性軸と判定例は [`docs/research/mercari/judgment_examples/`](../docs/research/mercari/judgment_examples/) を参照。

**現行実装の限界**: 現在の `research/analyze.js` と `research/rival_count.js` は「タイトル先頭 28 文字の正規化完全一致」でクラスタリングする実装であり、上記の前提を満たしていない。このため同一商品の取りこぼしが発生する。実体属性ベースの新実装は ground truth (正解リスト) 作成完了後に着手する (本手順書更新時点では未実装)。

## 採用中の検索手法: 14日ウィンドウ方式

Mercari内部APIを直接呼び出し、14日以内にSOLDになった全商品を収集・クラスタリングすることで売れ筋を特定する方式。

**実績（2026-04-12）**: 全10キーワード × 5価格帯 = 50組み合わせを約3分で完走。7,152件収集・23品の仕入れ候補を特定。トークン消費は軽微。

---

### ロジック概要

1. 入口キーワード（10種）× 価格帯（5区間）の組み合わせを並列で実行する
2. 各組み合わせについて、`SORT_CREATED_TIME DESC` + `STATUS_SOLD_OUT` + `itemConditionId=[1]` でSOLD一覧をAPI取得する
3. **14日境界**（現在時刻 - 14×86400 秒）に達するまで全ページを収集する
4. 全組み合わせの収集結果を `item.id` でユニーク化する
5. タイトルを正規化してクラスタリングし、3件以上のクラスターを売れ筋候補とする
6. 除外PDFと突合して禁止商品を除外する（第3段階）
7. 各候補について現在販売中のライバル数をカウントし、10人以上を除外する（第4段階）

---

### 価格帯の区切り

5区間 × 10キーワード = **50組み合わせ**を実行する。区間を小さくするほど1バケット内の件数が減り、14日境界に到達しやすくなる。

| 区間 | 範囲 |
|---|---|
| 1 | ¥800〜¥1,000 |
| 2 | ¥1,000〜¥1,200 |
| 3 | ¥1,200〜¥2,000 |
| 4 | ¥2,000〜¥3,000 |
| 5 | ¥3,000〜¥5,000 |

---

### 手順の全体フロー

**収集・分析のコードを自分で書かないこと。必ず以下のスクリプトを使うこと。**

```
research/collect.js      ← 収集（browser_evaluate で実行）
research/analyze.js      ← 分析（node で実行）
research/rival_count.js  ← 販売中ライバル数カウント（browser_evaluate で実行）
```

1. `browser_navigate` で `https://jp.mercari.com` の任意のページを開いて3秒待つ
    - 未ログインでよい。`collect.js` および `rival_count.js` が DPoP 認証キーを IndexedDB から取得するため、ブラウザで Mercari のセッションを確立しておく必要がある
2. `research/collect.js` の内容を読み取り、`browser_evaluate` の `function` パラメータにそのまま渡して実行する
3. 戻り値の `_filename` フィールドの値を使い、`research/` ディレクトリに JSON として保存する
4. `node research/analyze.js research/<保存したファイル名>` を実行する
5. 第3段階（禁止商品チェック・PDF突合）を実施する（下記「第3段階: 禁止商品チェック（PDF突合）」参照）
6. 第4段階（販売中ライバル数カウント）を実施する（下記「第4段階: 販売中ライバル数カウント（自動・販売中検索）」参照）
7. レポートを作成する（下記「レポート化（手動）」参照）

### 収集後処理

`analyze.js` が2段階の自動パイプライン（**第1段階**: タイトル正規化によるクラスタリング、**第2段階**: 価格一貫性・カテゴリ多数決・出品者数のメタデータフィルタ）で候補を絞り込み、その後、手動の禁止商品チェック（第3段階）とレポート化を行う。第1・第2段階の内部実装は [`docs/research/implementation-notes.md`](../docs/research/implementation-notes.md) を参照。

**`analyze.js` の出力**: 入力と同じディレクトリ（`research/`）に以下の2ファイルを生成する。

- `YYYY_MM_DD_HH_MM__candidates.json` — 3件以上のクラスターをメタデータ付きで格納（レポート化に使う主ファイル）
- `YYYY_MM_DD_HH_MM__clusters.json` — 全クラスターの概要（デバッグ用）

**`candidates.json` の `candidates` 配列の主要フィールド**:

| フィールド | 意味 |
|---|---|
| `representativeTitle` | 代表タイトル（1件目のアイテム名） |
| `count` | クラスター内のアイテム数（カテゴリフィルタ後） |
| `minPrice` / `maxPrice` | 価格帯 |
| `priceWarning` | 価格幅が2倍超（別商品混入の可能性あり・要目視確認） |
| `uniqueSellers` | ユニーク出品者数 |
| `excluded` | 除外フラグ（`true` の場合はレポート本文から除外し、末尾の除外一覧に記載する） |
| `exclusionReason` | 除外理由（例: `"sellers_10_or_more"`） |
| `thumbnails` | 代表サムネイルURL（最大3枚） |
| `items` | クラスター内の全アイテム（`id`・`name`・`price`・`url`・`sellerId`・`categoryId`・`thumbnail`） |

#### 第3段階: 禁止商品チェック

仕入れ候補から、法務・コンプライアンス上の禁止商品を除外する。**このチェックを通過しない候補はレポートに載せてはいけない**（ゲート条件）。

**手順:**

1. `references/注意商品.pdf` と `references/new仕入れ禁止商品_アパレル.pdf` を**全ページ、画像を含めて**読む
   - セッションメモリは持続しないため、毎回読み直す
   - テキスト抽出では拾えない情報（ロゴ・キャラクターデザイン・類似例）があるため画像も目視する
2. `*_candidates.json` の各候補について、タイトル・サムネイルをPDFの内容と突合する
3. 以下のカテゴリに該当するものは除外する:
    - ブランドロゴ／キャラクター／版権物／模倣品
    - PSE該当品（電気用品）／薬機法該当品（化粧品・医薬品等）／食品衛生法該当品
    - 動物素材（毛皮・ワシントン条約該当品等）
4. 除外した候補は**レポート末尾に「禁止商品チェックで除外」として件数・代表タイトル・除外理由を記録する**（トレーサビリティのため）

#### 第4段階: 販売中ライバル数カウント

第3段階を通過した候補について、メルカリの**現在販売中**の商品を検索して、同商品を扱っているライバル出品者数をカウントする。**10人以上のライバルがいる候補はレッドオーシャンとして除外する**（ゲート条件）。

ここで「ライバル」は次のすべてを満たす出品者を指す:

- メルカリで現在販売中（売り切れではなく現在出品中）の商品を出していて、
- 出品状態が新品・未使用、出品者種別が個人（事業者ショップではない）であり、
- 商品の最終更新日時が14日以内であり（14日以上前の商品は対象外。SEO対策をしていない出品者とは差別化できるという判断によりカウントしない）、
- その商品が候補クラスターと**同じ商品**である（判定方法は後述）

「同じ商品」の判定は `analyze.js` の第1段階クラスタリングと同じ正規化処理で機械的に行う:

- タイトルから記号類を除去
- 数字をすべて `N` に置換
- 連続する空白を1つに、前後の空白を除去
- 先頭28文字を取り出す
- これが候補クラスターの `key` フィールド（同じ正規化後の文字列）と一致するなら同じ商品と見なす

**※この先頭28文字一致方式は前述の「同一商品判定の前提」で述べた通り、タイトルを変えて出品する実務慣習を反映できていない暫定実装。同一商品の取りこぼしが発生する。実体属性ベースの新実装に置き換え予定。**

`analyze.js` が `*_candidates.json` に出力する `uniqueSellers` フィールドは「過去14日に売れた商品の出品者数」であり、ここで言う「販売中ライバル数」とは別物（売れた人数 ≠ 現在販売中の人数）。本段階で別途カウントする必要があるのはこのため。

**手順:**

1. `*_candidates.json` の各候補について、人間が手作業で検索するときと同じような検索キーワードを考える
   - 代表タイトルをそのまま使うのではなく、商品が特定できる2〜3語を抜き出す
   - 例: 代表タイトルが「レインコート レインポンチョ 自転車 厚手 ウエア 紺 男女 雨具 梅雨 310」なら、検索キーワードは「レインポンチョ 自転車」
2. `browser_evaluate` で `window.__RIVAL_INPUT__` に入力配列を設定する。配列の各要素は以下のオブジェクト:
   - `clusterKey`: 候補の `items[0].id`（後で `*_rivals.json` と `*_candidates.json` を結合するためのキー）
   - `query`: 1で考えた検索キーワード
   - `normalizedPrefix`: 候補の `key` フィールドの値（同じ商品判定に使う）
3. `research/rival_count.js` の内容を読み取り、`browser_evaluate` の `function` パラメータにそのまま渡して実行する
4. 戻り値の `_filename` フィールドの値を使い、`research/` ディレクトリに JSON として保存する（`*_rivals.json`）

**`*_rivals.json` の主要フィールド:**

| フィールド | 意味 |
|---|---|
| `results[].clusterKey` | 結合キー（候補の `items[0].id` と一致する） |
| `results[].rivalCount` | 同商品で個別出品者として数えた数 |
| `results[].rivalSellers` | 出品者IDのリスト（重複を除いたもの） |
| `results[].rivalQuery` | 使った検索キーワード |
| `results[].rivalExcluded` | `rivalCount` が10以上のとき `true`（除外確定） |
| `results[].pagesScanned` | 何ページ取得したか（デバッグ用） |
| `results[].error` | 失敗時のみエラーメッセージ |

### レポート化

第3段階・第4段階を通過した候補をレポート化する。**この段階でクラスターの統合・分割・同一性判定を行わない**（`adr/adr_2026_04_12_Claudeによるクラスター検証ステップの導入.md` で却下済み。理由: 第1段階の精度が高く介入は候補消失リスクの方が大きい）。

**手順:**

1. `*_candidates.json` の `candidates` 配列を順番に処理する（上限なし・全件）
2. `*_rivals.json` の `results` 配列を、`clusterKey`（= 候補の `items[0].id`）で結合する
3. 以下のいずれかに該当する候補は仕入れ候補リストから外し、レポート末尾の対応セクションに記録する:
    - `*_candidates.json` の `excluded: true`（`exclusionReason: "sellers_10_or_more"`）→ 「過去14日売れた出品者数で除外したクラスター」
    - 第3段階（禁止商品チェック）で除外したもの → 「禁止商品チェックで除外したクラスター」
    - `*_rivals.json` の `rivalExcluded: true` → 「販売中ライバル10人以上で除外したクラスター」
4. 残った候補を `reports/YYYY/MM/` に Markdown で保存する

**絶対禁止事項:**

- `slice(0, N)` や「上位のみ」「厳選」「代表的なもの」等の理由で候補を間引くこと。**3つの除外条件のいずれにも該当しない候補は全件レポートに掲載する**
- タイトル・サムネイルを見て「これは同一商品ではない」「これは別商品」等の意味判断でクラスターを分割・統合・除外すること。クラスタリングの誤りはすでに第1段階の recall 重視方針で許容している（`priceWarning` フラグで識別可能）

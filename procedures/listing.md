# 出品手順 (フリマサイト)

本手順書は対応販路ごとに章を持つ。現時点では **メルカリ**、**ヤフーフリマ**、**ヤフオク (フリマ形式)** に対応する。共通章 (出品方法・前提条件・制約事項・CSV 仕様・状態管理) と販路別章 (フォーム入力フロー・トラブル対応) を読み分けること。

## やりたいこと

本ドキュメントは [`overview.md`](../overview.md) の **出品・販売・SEO対策** の手順書である。

商品リサーチから写真撮影・商品説明ページ作成まで完了した中国輸入商品を、メルカリ・ヤフーフリマ・ヤフオクの出品フォームに登録するまでの作業を扱う。出品後の値下げ・問い合わせ対応・梱包・発送はそれぞれ別工程で扱う。

---

## 採用する出品方法

本手順では、**Claude Code (CLI 型の AI アシスタント) が Playwright (ブラウザ自動操作ライブラリ) を MCP (Model Context Protocol) 経由で操作して各販路の出品フォームを 1 件ずつ埋める方式**を採用する。

具体的には:

1. ユーザーが Claude Code セッションを起動する
2. Claude Code が Playwright で Chromium ブラウザを起動する (永続コンテキスト = ログイン状態がディスクに保存され、次回起動時も維持される)
3. **初回のみ**、ユーザーが手動で各販路にログインする (2 段階認証含む)
4. Claude Code が CSV を読み、画像をアップロードしてフォームの各項目を入力する
5. 1 件出品するたびにスナップショットで状態を確認し、ユーザーが結果を確認できる

完全自動の Node.js スクリプトを cron 等で無人実行する方式は採用しない。理由は次節。

## なぜ完全自動スクリプトでないのか

### 規約上の理由

#### メルカリ

メルカリ運営は 2017 年に**「自動出品ツール (メルカリに自動で出品を行うソフトウェア等) の利用を禁止」**することを公式発表している ([運営プレスリリース 2017-06-16](https://about.mercari.com/press/news/articles/20170616_anti-fraud/))。さらに [メルカリガイド「その他、不適切と判断される行為」](https://help.jp.mercari.com/guide/articles/900/) には「弊社が提供するインターフェイスとは別の手法を用いてサービスにアクセスすること」が禁止行為として列挙されている。

#### ヤフーフリマ

[Yahoo!フリマ ガイドライン](https://paypayfleamarket.yahoo.co.jp/guide/guideline/) および [Yahoo!オークション/フリマの自動化禁止ポリシー (LY Corporation 利用規約)](https://www.lycorp.co.jp/ja/company/terms/) で、サービス運営妨害目的のロボット利用および本来想定しないインターフェイス経由のアクセスが禁止されている。一次ソースの厳密な節番号は別途確認要 (TODO)。

#### ヤフオク

[Yahoo!オークション ガイドライン細則](https://auctions.yahoo.co.jp/topic/notice/policy/) でも自動化ツール・ロボットによる入札/出品が禁止されている。一次ソースの厳密な節番号は別途確認要 (TODO)。

無人の自動出品スクリプトは前者・後者いずれにも該当する可能性が高い。

### 検知の観点

メルカリの bot 検知は大きく分けて 3 層で構成されると考えられる:

| 層 | 内容 | 完全自動スクリプト | Claude Code + MCP |
|---|---|---|---|
| 指紋層 | `navigator.webdriver` 等のブラウザ指紋 | Playwright を使う限り検知される | 同上 |
| 行動層 | アクション間隔・タイピング・マウスの自然さ | ループ実行のため機械的 | 思考時間・対話で**自然にバラつく** |
| ボリューム層 | 1 セッションでの出品数・速度 | プログラムでいくらでも速くできる | 対話のため自然と数件/セッションに収まる |

指紋層は両者同等にバレる余地があるが、行動層・ボリューム層は Claude Code 経由の方が実質的に検知されにくい。

### UI 変更への耐性

メルカリは定期的に UI を変更する。完全自動スクリプトはセレクタや遷移パターンが変わると壊れる。Claude Code 経由なら予期せぬダイアログ (例: ウィザード遷移、確認モーダル) にも臨機応変に対応できる。

### 注意

上記の検知層比較は理論上のものであり、**Claude Code + MCP 経由でも検知される可能性はゼロではない**。本手順の他の制約 (出品ペース・実物画像など) を厳守すること。

## 前提条件

### 環境

- Claude Code がインストール済み
- Playwright MCP サーバが設定済み (`mcp__playwright__browser_*` ツールが利用可能)
- Chromium が Playwright 経由で起動できる状態

### アカウント

販路ごとの事前準備を完了させておく。未完了だと出品時にダイアログでブロックされる。

- **メルカリ**: 個人アカウントが作成済み + **本人確認完了** (信頼スコア向上、配送選択肢の解放、出品上限の緩和)
- **ヤフーフリマ**: Yahoo! JAPAN ID 作成済み + **本人情報の登録完了** (氏名/カナ/電話/郵便番号/住所)。未登録だと「出品する」ボタン押下時に「あなたの情報」ダイアログが出て止まる。事前にプロフィール画面から登録しておくこと
- **ヤフオク**: Yahoo! JAPAN ID 作成済み + **出品者情報の登録完了** (氏名・住所等) + **Yahoo!ウォレット登録完了** (PayPay 連携または受取銀行口座)。両方が揃わないと確認画面に「出品する」ボタンが表示されず、代わりに「登録してください」リンクが出る
- 初回利用時はユーザーが手動で各販路にログインする (Playwright の永続コンテキストにログイン状態が保存される。Yahoo! JAPAN ID はヤフーフリマとヤフオクで共通)

### 入力データ

各「出品バッチ」(=同時期に出品する商品群) は次のディレクトリ構造で配置する:

```
listings/runs/YYYY_MM_DD/
├── YYYY_MM_DD_listing.csv     # 出品予定リスト (本手順の入力)
├── status.json                # 出品状態の管理ファイル (初回はファイル無しで OK)
└── {id}/                      # 各 id ごとの画像ディレクトリ
    ├── image1.jpg
    ├── image2.jpg
    └── ...
```

- `YYYY_MM_DD` は出品バッチを開始する日付 (JST)
- `{id}` は CSV の `id` カラムに対応する 3 桁ゼロ埋め連番 (`001`, `002`, ...)
- CSV のスキーマは [§ CSV 仕様](#csv-仕様) を参照
- 画像のスキーマは [§ 画像の要件](#画像の要件) を参照

## 制約事項 (必読、BAN 対策)

メルカリは出品ペースや内容の異常を検知するとアカウントを段階的に制限する (警告 → 一時利用制限 24時間〜1週間 → 無期限利用停止)。以下を厳守する。

### 1. 出品ペース
``
[メルカリ運営公式の出品ポイント PDF](../references/%E3%80%90%E5%87%BA%E5%93%81%E3%81%AE%E3%83%9D%E3%82%A4%E3%83%B3%E3%83%88%E3%83%BB%E6%B3%A8%E6%84%8F%E7%82%B9%E3%80%91.pdf) には次の 2 つの上限が示されている (両方守る必要がある):

- **短時間上限**: 10〜30 分以内に 10 件以上の出品・削除は NG
- **1 日上限**: 1 日トータルで 30〜50 件以上の出品・削除は NG

これらを安全側に守るため、本手順では次の運用ルールを設ける:

| 運用ルール | 数値 | どの上限を防ぐか |
|---|---|---|
| 1 セッションでの出品数 | **5 件以内** (PDF の「1 回の作業で 5 件以内推奨」に準拠) | 短時間上限 |
| セッション間の間隔 (前セッションの終了 → 次セッションの開始) | **最低 30 分** | 短時間上限 |
| 1 日トータル | **20 件以内** | 1 日上限 (PDF の 30〜50 件 NG ラインの 2/3 に抑える) |
| 月 100 件のペース配分 | 上限 20 件/日の範囲で運用。例: 1 日 5 件 × 営業日、または 1 日 20 件 × 5 日など柔軟に運用 | 1 日上限の範囲内 |
| 同一商品の削除→再投入 | **本工程では行わない** | PDF「動作数」を温存。動作数の上限超過で出品制限がかかる。SEO 目的の再投入は SEO 工程の責務 |

#### 運用ルールが PDF 上限を満たすことの確認

- **短時間上限 (10〜30 分で 10 件以上 NG)**: 1 セッション 5 件 + セッション間 30 分間隔の場合、任意の 30 分窓に含まれる出品は最大 5 件 (2 セッション分が同じ 30 分窓に入ることはない)。よって 10 件未満を必ず満たす。出品数を増やしてもこの不等式は変わらない (4 セッションで 20 件出しても、各 30 分窓には最大 5 件のまま)。
- **1 日上限 (30〜50 件以上 NG)**: 1 日 20 件以内に明示的に制限しているため、PDF 下限 (30 件) の 2/3 で抑える。

### 2. 自動化検知への意識

- 同じ Playwright 永続コンテキストを継続使用する (毎回ログインし直さない)
- 1 件出品するごとに**スナップショットで状態確認**してから次に進む
- セッションを起動しっぱなしにせず、出品終了時はブラウザを閉じる (長時間ヒープに残すと検知される可能性)

## CSV 仕様

### 重要: CSV はいかなる理由があろうと変更しない

`listing.csv` は run 開始時に確定したら、**いかなる理由があろうと変更してはいけない**。

- 商品情報に誤りが見つかった場合も、CSV を直接書き換えない
- 出品済み・出品失敗などの状態を CSV に書き戻さない (状態は [`status.json`](#状態管理-statusjson) で管理する)
- 商品の追加が必要な場合は、新しい run ディレクトリを作り直す
- Claude Code は本工程の実行中、いかなる場合も `listing.csv` への書き込み・編集を行わない

理由:

- 出品時点の正確な記録が後から追えなくなる (監査不能)
- CSV の編集と状態管理 (`status.json`) が並行すると整合性が崩れる
- Excel 等の外部ツールで誤編集されたとき、元の状態に戻せない

### スキーマ

`listings/runs/YYYY_MM_DD/YYYY_MM_DD_listing.csv`:

CSV は UTF-8、ヘッダー行付き。各セルが改行を含む場合はダブルクォートで囲む (RFC 4180 準拠)。

| カラム | 必須 | 内容 | 制約・例 |
|---|---|---|---|
| `id` | ◎ | run 内一意の識別子 | 3 桁ゼロ埋め連番 (`001`〜`999`) |
| `商品名` | ◎ | 出品タイトル | 40 文字以内 |
| `商品の説明` | ◎ | 説明文 (改行可) | 1000 文字以内 |
| `カテゴリー1`〜`カテゴリー4` | ◎ | カテゴリー階層 (4 階層) | 例: `ファッション` / `メンズ` / `トップス` / `その他` |
| `サイズ` | ◎ | カテゴリー依存のサイズ | 例: `L`、`27.5cm`、`Free` |
| `商品の状態` | ◎ | 6 段階のいずれか | `新品、未使用` / `未使用に近い` / `目立った傷や汚れなし` / `やや傷や汚れあり` / `傷や汚れあり` / `全体的に状態が悪い` |
| `配送料の負担` | ◎ | 通常は出品者負担 | `送料込み(出品者負担)` (本人確認すると `着払い(購入者負担)` も選択可) |
| `配送の方法` | ◎ | 配送業者・サービス | 例: `ゆうゆうメルカリ便`、`らくらくメルカリ便` |
| `送料` | ◎ | 出品判断時に確定済みの送料 (整数の円) | 例: `215`、`410`、`750`。利益率計算に使うため出品前に決まっている前提。ヤフオクのサブサービス選択にも使う |
| `発送元の地域` | ◎ | 47 都道府県のいずれか | 例: `和歌山県` |
| `発送までの日数` | ◎ | 3 段階のいずれか | `1~2日で発送` / `2~3日で発送` / `4~7日で発送` |
| `価格` | ◎ | 整数 (円) | 300 以上 |
| `商品の特徴` | △ | カテゴリー依存の特徴項目 | 例: `汚れ・破れ・臭いなど: なし` |
| `画像1`〜`画像20` | ◎ (最低 1) | 画像の CSV からの相対パス | 例: `001/image1.jpg` |

注意:

- `画像1` が各販路のサムネイル画像になる
- `画像1`〜`画像20` のカラム順がアップロード順 (商品ページで表示される順) になる
- 必要な画像枚数だけ埋め、残りは空欄でよい

### 販路別の値マッピング

CSV はメルカリ用語をベースにして書く。販路差は出品時に Claude が下表で変換する。

| CSV カラム | CSV 値 (メルカリ準拠) | メルカリ UI 上の選択肢 | ヤフーフリマ UI 上の選択肢 | ヤフオク UI 上の選択肢 |
|---|---|---|---|---|
| 配送の方法 | `ゆうゆうメルカリ便` | ゆうゆうメルカリ便 | おてがる配送（日本郵便） | おてがる配送 (日本郵便系: ゆうパケット 等) |
| 配送の方法 | `らくらくメルカリ便` | らくらくメルカリ便 | おてがる配送（ヤマト運輸） | おてがる配送 (ヤマト系: ネコポス・宅急便コンパクト・宅急便) |
| 発送までの日数 | `1~2日で発送` | 1~2日で発送 | 1~2日 | 1〜2日 |
| 発送までの日数 | `2~3日で発送` | 2~3日で発送 | 2~3日 | 2〜3日 |
| 発送までの日数 | `4~7日で発送` | 4~7日で発送 | 3~7日 | 3〜7日 |
| 商品の状態 | `新品、未使用` | 新品、未使用 | 未使用 | 未使用 |
| 商品の状態 | `未使用に近い` | 未使用に近い | 未使用に近い | 未使用に近い |
| 商品の状態 | `目立った傷や汚れなし` | 目立った傷や汚れなし | 目立った傷や汚れなし | 目立った傷や汚れなし |
| 商品の状態 | `やや傷や汚れあり` | やや傷や汚れあり | やや傷や汚れあり | やや傷や汚れあり |
| 商品の状態 | `傷や汚れあり` | 傷や汚れあり | 傷や汚れあり | 傷や汚れあり |
| 商品の状態 | `全体的に状態が悪い` | 全体的に状態が悪い | (該当なし) → ユーザーに判断を仰ぐ | 全体的に状態が悪い |

ヤフオクの配送方法は CSV の親サービス名 (`ゆうゆうメルカリ便` 等) だけでは決まらない。サブサービス (ゆうパケット/ゆうパケットプラス/ゆうパック 等) は **CSV の `送料` 列の値から逆引き**して決める。

| CSV `送料` 値 | ヤフオクで選ぶサブサービス (おてがる配送 日本郵便系) | 制約 |
|---|---|---|
| 160 | ゆうパケットポストmini | 16.8×21.1cm 内、専用封筒、2kg まで |
| 210 | ゆうパケットポスト | 60cm 内、専用箱/シール、2kg まで |
| 215 | ゆうパケット | 60cm 内、厚さ 3cm まで、1kg まで |
| 410 | ゆうパケットプラス | 24×17cm 内、専用箱、厚さ 7cm まで、2kg まで |
| 750 以上 | ゆうパック | 170cm 内、25kg まで |

ヤマト運輸系を選ぶ場合 (CSV `配送の方法` が `らくらくメルカリ便` の場合) も同様に送料からサブサービスを逆引き (ネコポス 210 円 / 宅急便コンパクト 490 円 / 宅急便 750 円〜)。

**CSV `送料` が空欄の場合は出品判断ワークフロー上のバグ** (本来は仕入れ判断時点で送料が確定しているはず) なので、Claude は推測せず必ずユーザーに質問してから出品する。

### CSV にない販路独自項目 (ヤフーフリマ)

ヤフーフリマはカテゴリ選択直後に動的属性枠が出現する (例: メンズトップスなら ブランド/性別/色/着用回数/サイズ S/M/L)。これらは CSV に列を持たない。カテゴリ依存で項目自体が変わるため、属性枠の構造は出品時にスナップショットで都度確認する。

**ブランドは原則として空欄にする。** 本プロジェクトの中国輸入物販はノーブランド品が大半なので、ブランド欄は**デフォルトで空欄が正しい状態**である。例外は CSV・商品名・商品説明に明確なブランド名が記載されている場合のみで、そのときだけそのブランドを入力する。販路が商品名から自動推定したブランドは誤りが多いため、まず削除してから上記の基準で判断する (推定値をそのまま採用しない)。

ブランド以外の属性の入力方針 (上から順に判定する):

1. **CSV / 商品名 / 商品説明から確度高く値が決まる場合** → Claude がその値を入力する
   - 例: 商品説明に「カラー: ブラック」とある → 色項目に「黒」を入れる
2. **商品にその属性が存在しない (該当選択肢なしを含む) と Claude が判断できる場合** → 空欄のまま進める
   - 例: ユニセックス商品 → 性別空欄
   - 例: 新品出品なのに「着用回数」項目がある → 空欄
3. **推測になる (確度が低い) 場合** → ユーザーに該当項目と候補を提示して質問する
4. **商品情報からは判定不能な場合** → ユーザーに該当項目を提示して質問する

適当に埋めない。誤入力は検索フィルタからの離脱を招き販売機会を損なう。判断に迷ったら 3 / 4 として必ず質問する。

### CSV にない販路独自項目 (ヤフオク)

ヤフオクは CSV にない次の項目が出品時に必須になる:

| 項目 | 値 | 理由 |
|---|---|---|
| 販売形式 | **フリマ（定額）** に切替 | デフォルトはオークション。中国輸入物販はオークション運用しないため、必ず radio で切替 |
| 終了する日時 (日付) | **3 日後** | [`references/各フリマサイトのSEOのやり方.pdf`](../references/%E5%90%84%E3%83%95%E3%83%AA%E3%83%9E%E3%82%B5%E3%82%A4%E3%83%88%E3%81%AESEO%E3%81%AE%E3%82%84%E3%82%8A%E6%96%B9.pdf) の SEO 推奨に準拠 (「3 日以内に設定する人が多い」) |
| 終了する日時 (時間帯) | **「午後 9 時から午後 10 時」** を選択 (21〜22 時に掲載終了) | 同 PDF の「終了時間は 21-22 時頃に掲載終了がおすすめ」に準拠 |
| 送料負担 | 出品者 (デフォルトのまま) | CSV「配送料の負担」が `送料込み(出品者負担)` であることに対応 |

## 画像の要件

メルカリ側の仕様:

- 形式: JPG または PNG
- サイズ: 1 枚あたり 10MB 以下を推奨
- 枚数: 1 件あたり 1〜20 枚

画像の中身 (実物撮影が必要か、加工をどこまでするか等) は写真撮影・商品説明ページ作成工程で担保される前提。本工程では用意された画像をそのままアップロードする。

## 1 件あたりの出品フロー

Claude Code が CSV を読みながら、以下のステップを実行する。

### Step 1: 対象の選定

1. ユーザーから出品先の販路を確認する (`mercari` / `yahoo_flea` / `yahoo_auction`)
2. `listings/runs/YYYY_MM_DD/status.json` を読む (ファイル無し時は全 id × 全販路を `未出品` 扱い)
3. 選んだ販路について、`status` が `未出品` の最初の id を選ぶ
4. CSV から該当行を読む
5. `{id}/` 配下の画像ファイルが CSV の `画像1`〜`画像N` カラムと整合しているか確認
6. 文字数・必須項目を確認 (販路差は出品時にマッピング表で吸収する前提で、CSV はメルカリ準拠で検証)
   - 商品名: 40 文字以内 (ヤフマ単独運用なら 65 文字までだが、両販路出品を想定し短い方に合わせる)
   - 商品の説明: 1000 文字以内
   - 価格: 300〜300,000 (ヤフマ上限に合わせる。メルカリ単独なら上限なし)
   - 必須カラム (id, 商品名, 商品の説明, カテゴリー1〜4, サイズ, 商品の状態, 配送料の負担, 配送の方法, 送料, 発送元の地域, 発送までの日数, 価格, 画像1) が埋まっている

不備があれば中止してユーザーに報告。

   - メルカリ: ダイアログ内の「出品した商品をみる」リンクから `m{12 桁}` を抽出
   - ヤフーフリマ: 出品商品ページの URL (`https://paypayfleamarket.yahoo.co.jp/item/z{9 桁}`) から `z{9 桁}` を抽出
   - ヤフオク: 出品商品ページの URL (`https://auctions.yahoo.co.jp/jp/auction/{a-z}{10 桁}`) から `{a-z}{10 桁}` を抽出 (例: `o1164929607`, `j1228472137`)
3. `status.json` の該当販路ノードを更新:

```json
{

    "mercari": {
      "status": "出品済み",
      "item_id": "m10468438509",
      "listed_at": "2026-05-10T15:50:00+09:00"

```

### Step 4: 次に進むか、セッションを終了するか

- 同セッション内で続けて出品する場合: **最低 30 分待機** してから Step 1 へ戻る
- 5 件出品済み、または 30 分間隔を空けにくい状況 → セッション終了。次は最低 30 分後 (推奨: 数時間後または翌日) に再開
- セッション終了時は Chromium を閉じる (永続コンテキストはディスクに保存されているので次回も使える)

## 状態管理: `status.json`

CSV (出品予定リスト) は不変として扱い、状態は別ファイル `status.json` で管理する。

理由:

- CSV をクリーンに保ち、Excel 等で誤編集されるリスクを下げる
- 状態遷移が独立しているので、CSV と状態を同時編集して競合する事故を防げる
- 出品履歴の監査が容易 (どの id がいつ出品されたかが 1 ファイルに集約される)

### スキーマ

販路別に独立した出品状態を持つ。

```json
{
  "<id>": {
    "<channel>": {
      "status": "未出品" | "出品済み" | "出品失敗",
      "item_id": "<販路の item ID>",
      "listed_at": "2026-05-10T15:50:00+09:00",
      "failed_at": "2026-05-10T16:00:00+09:00",
      "failure_reason": "<理由>"
    }
  }
}
```

- `<channel>` は販路キー: `mercari`、`yahoo_flea`、または `yahoo_auction`
- `status` のみ全状態で必須
- `item_id` と `listed_at` は `出品済み` 時のみ
- `failed_at` と `failure_reason` は `出品失敗` 時のみ
- 日時は ISO 8601 + JST オフセット (`+09:00`)

例 (id=001 をメルカリ出品済み・ヤフマ未出品の状態):

```json
{
  "001": {
    "mercari": {
      "status": "出品済み",
      "item_id": "m10468438509",
      "listed_at": "2026-05-10T15:50:00+09:00"
    },
    "yahoo_flea": {
      "status": "未出品"
    },
    "yahoo_auction": {
      "status": "未出品"
    }
  }
}
```

`item_id` の形式は販路ごとに異なる:

- メルカリ: `m{12 桁}` (例: `m10468438509`)
- ヤフーフリマ: `z{9 桁}` (例: `z609698488`)
- ヤフオク: `{a-z}{10 桁}` (例: `o1164929607`, `j1228472137`)

### `status.json` が無い場合 / 販路ノードが無い場合

初回起動時は `status.json` が存在しない。その場合は CSV の全 id × 全販路を `未出品` 状態として扱う。

販路ノードが無い id (例: メルカリだけ出品済みでヤフマノードが無い) も、その販路では `未出品` 扱い。

Step 3 で初めて出品成功した時点で Claude Code が `status.json` の該当販路ノードを作成・更新する。

## トラブル対応

### 共通

#### ログインセッション切れ
- 症状: 出品フォーム URL にアクセスしたらログインページにリダイレクトされた
- 原因: 永続コンテキストに保存されたログインセッションが期限切れ
- 対処: ユーザーが手動でログイン (2 段階認証含む)。永続コンテキストに自動保存されるので、次回以降は不要

#### 「出品する」がグレーアウト
- 症状: フォーム入力後、「出品する」ボタンが押せない
- 原因: 必須項目漏れ
- 対処: スナップショットで全項目を確認し、漏れている項目を埋める

#### 画像アップロード失敗
- 確認: 画像が 21 枚以上ないか、ファイルサイズが極端に大きく (例: 50MB 超) ないか、JPG/PNG 形式か
- 対処: 該当画像を差し替え or 削除して再試行

#### 出品ペースの累積警告
- 症状: 「短時間に多くの出品をされています」等の警告が出る
- 対処: その日の出品を**中止**。最低 24 時間休止してから再開

### メルカリ固有

#### wizard リダイレクト (カテゴリー「その他」等)
- 症状: カテゴリー選択直後に `/sell/wizard` (製品情報・モデル入力画面) に飛ぶ
- 原因: 「その他」を含むカテゴリーを選んだ場合、メルカリ側が製品情報の追加入力を促す
- 対処: 「出品画面に戻る」ボタンをクリックでスキップ。入力済み項目は保持される

#### 「商品の特徴」選択時の説明文自動追記
- 症状: 「商品の特徴」(例: 汚れ・破れ・臭いなど) で「なし」を選ぶと、説明文末尾に `汚れ・破れ・臭いなど...なし` が自動追加される
- 対処: 「商品の特徴」を選択した**後**に「商品の説明」を再 fill して上書きする (Step 2-A の順序を 2-A-9 → 2-A-10 にしているのはこのため)

#### Mercari item ID の取得失敗
- 症状: 「出品が完了しました」ダイアログから URL が読めない
- 対処: マイページ `/mypage/listings` を開き、最新の出品 (作成日時が最も新しいもの) の URL から item ID を取得

### ヤフーフリマ固有

#### 「あなたの情報」ダイアログ (本人情報未登録)
- 症状: 「出品する」ボタン押下後に「あなたの情報」ダイアログが出て止まる (姓・名・カナ・電話番号・住所の入力欄)
- 原因: Yahoo!フリマで本人情報が未登録
- 対処: ユーザーがダイアログに直接入力して「登録して出品する」を押す。または出品フォームに戻り、事前にプロフィール画面から本人情報を登録してから出品操作をやり直す。**Claude は個人情報なので入力しない**

#### ブランド自動推定の誤り
- 症状: カテゴリ選択後、商品名から推定された別レーベルがブランド枠に入る (例: 「URBAN RESEARCH」入力で「URBAN RESEARCH DOORS」が誤推定)
- 対処: ブランド枠の削除ボタンを押して消す → autocomplete で正しいブランドを検索して選択。中国輸入のノーブランド商品なら空欄のまま進める

#### ハッシュタグ自動付与の誤り
- 症状: ブランド連動でハッシュタグが自動付与される (例: `#urbanresearchdoors`)
- 対処: 該当ハッシュタグの削除ボタンで消す。ブランドを正しいものに修正すると追従更新される場合もあるが、念のため確認

#### カテゴリ依存の動的属性枠
- 症状: カテゴリ選択直後に未知の属性 (例: 着用回数、カラー、性別等) が出現
- 対処: [§ CSV にない販路独自項目](#csv-にない販路独自項目-ヤフーフリマ) の 4 段階方針に従う

#### Yahoo!フリマ item ID の取得失敗
- 症状: 出品完了後、URL から item ID (`z{9 桁}`) が読めない
- 対処: マイページの出品一覧から最新の出品ページに遷移し、URL `https://paypayfleamarket.yahoo.co.jp/item/z{9 桁}` から item ID を取得

### ヤフオク固有

#### キャンペーンモーダルがクリックを妨害
- 症状: 出品フォーム表示直後にキャンペーン (PayPay マツリ等) のモーダルが手前に出て、画像追加・販売形式切替などのクリックが効かない
- 対処: JS で `document.getElementById('js-CampaignPRModal').style.display='none'` および `js-CampaignPRModal_filter` も同様に閉じる

#### 画像 input が直接クリックできない
- 症状: `<input type=file id=selectFileMultiple>` を直接クリックしようとすると label/span が手前にあるためエラー
- 対処: `label[for="selectFileMultiple"]` を JS で `.click()` する → file chooser が開く

#### 販売形式デフォルトがオークション
- 症状: 何もしないとオークション形式で出品される
- 対処: `#salesmode_buynow` radio を必ず click してフリマ形式に切り替える

#### 説明欄が WYSIWYG iframe
- 症状: 説明欄は iframe 内の contenteditable body で、通常の textbox 入力ができない
- 対処: `iframe#rteEditorComposition0` の `contentDocument.body.innerHTML` に JS で書き込む。改行は `<br>` に変換

#### カテゴリの「このカテゴリに出品」ボタン押し忘れ
- 症状: カテゴリ階層の行をクリックしただけで戻ってきてしまい、カテゴリが未確定のまま
- 対処: 行をクリックした後、必ず「このカテゴリに出品」ボタンを押して確定 → 元の出品フォームに戻る

#### 出品者情報・Yahoo!ウォレット未登録で「出品する」ボタンが出ない
- 症状: 確認画面まで進んでも、「出品する」ボタンの位置に「出品者情報の登録」「Yahoo!ウォレットの登録」リンクが表示されている
- 対処: 物販オーナー側で事前に登録を済ませる ([§ 前提条件 - アカウント](#アカウント) 参照)。本人確認運用しないアカウントではヤフオク出品はできない

#### Yahoo!オークション item ID の取得失敗
- 症状: 出品完了後、URL から item ID (`{a-z}{10 桁}`) が読めない
- 対処: マイオーク (`https://auctions.yahoo.co.jp/jp/show/mystatus`) の出品中商品一覧から最新の出品ページに遷移し、URL `https://auctions.yahoo.co.jp/jp/auction/{a-z}{10 桁}` から item ID を取得
